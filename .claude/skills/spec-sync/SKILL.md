# spec-sync — 스펙 문서 갱신·정합 감사

## 문서 역할 분담

| 문서 | 담는 것 | 담지 않는 것 |
|---|---|---|
| REQUIREMENTS.md | FR/NFR(무엇을), 우선순위, 트레이서빌리티(§6), CLI 사양(§5) | 구현 방법, 클래스 구조 |
| DESIGN.md | 컴포넌트·메서드(§2), 플로우(§3), 스키마(§5), 검증 설계(§9), 설계 결정 DQ(§10) | 요구사항 원문 중복 |

## FR 추가/수정 절차

1. 기존 FR 전체 훑기 — 겹치는 FR이 있으면 새 번호 대신 기존 FR에 하위 항목 추가
2. FR 표 형식 준수: `| FR{N}.{M} | 요구사항 | 우선순위(필수/선택/비고) |`
3. **기술 제약이 요구사항 해석을 바꾸면 FR 본문이나 비고에 명시** — 예: flat 스캔 날짜 미제공(FR17.5), ChromaDB 리스트 불가(FR15.3). 이유: 제약을 모르는 다음 구현자가 "왜 이렇게 설계했지"를 되물으며 잘못 단순화하는 것을 막는다
4. DESIGN.md 대응 갱신: §2 컴포넌트(메서드 시그니처 수준) · §3 플로우(신규 흐름이면) · §5 스키마(파일/API 형태 변경 시) · §10 DQ(아키텍처 결정이 있었으면 근거와 함께)
5. §6 트레이서빌리티에 `| FR{N}.{M}~ | 구현 컴포넌트 | 산출 아티팩트 |` 행 추가
6. 두 문서 버전 헤더 동기화 (버전·작성일·연계 문서·주요 변경)
7. 미구현 설계는 "구현 예정" 표기 — 구현 완료 시 표기 제거가 Phase 5(문서 동기화)의 일이다

## 검증 항목 추가 절차

- 단위(mock 가능) → `V-U{N}`, 네트워크 통합 → `V-I{N}`, 기능/대시보드 시나리오 → `V-D{N}` — DESIGN §9의 다음 번호를 잇는다 (2026-09-27 기준 다음 번호: **V-U41** · V-I9 · **V-D25** — FR35가 V-U22~27·V-D17~19, FR35 QA 결함 수정이 V-U28, 멤버십 감지 언어 비의존(FR13.7·DQ-38)이 V-U29, FR36(채널 메모·추출 탭 이름 변경·탭 간 자동 갱신)이 V-U30~31·V-D20, 종목코드 문맥 판정(FR12.2·DQ-43)이 V-U32, FR37(주기 자동 추출)이 V-U33~34·V-D21, FR38(정합 감사·건전성 점검)이 V-U35~36·V-D22, FR39(영상 단위 출처 기록 `origin`)가 V-U37~38·V-D23, **FR40(자막 용어 교정 1단계)이 V-U39~40·V-D24**를 선점). DQ 다음 번호는 **DQ-73**(DQ-31~37 = FR35, DQ-38 = FR13.7, DQ-39~42 = FR36, DQ-43 = FR12.2 종목코드 문맥 판정, DQ-44~50 = FR37 주기 자동 추출, DQ-51~57 = FR38 정합 감사·건전성 점검, DQ-58~63 = FR39 영상 단위 출처 기록, **DQ-64~72 = FR40 자막 용어 교정 1단계**)
- **이 포인터들은 이제 기계가 대조한다** — `./yt.sh audit`의 `audit.next-pointers`(FR38.11)가 이 문장의 값과 정본의 최대값+1을 비교한다. 번호를 선점하면 이 줄과 DESIGN §9.1 머리말을 **같은 커밋에서** 고친다. pytest 기준선(5곳)도 `audit.pytest-baseline`이 대조한다
- **V-U 번호의 정본은 `tests/test_unit.py`의 섹션 헤더 주석이다.** 번호를 부여·변경하면 DESIGN §9.1a와 테스트 주석을 같은 커밋에서 함께 고친다. 테스트에 번호를 붙이지 않은 검증은 DESIGN §9.1b(번호 미부여)에 FR 헤더 그대로 기록하고, 문서가 임의로 번호를 만들지 않는다
- 각 항목은 "절차 + 합격 기준" 형태로 작성. 합격 기준은 관찰 가능한 값(개수·상태·HTTP 코드)이어야 한다

## 정합 감사 (drift audit)

주기적으로 또는 "정합 확인" 요청 시 **기계에 맡긴다** (FR38):

```bash
./yt.sh audit                                  # 8검사 · 1초 이내 · output/ 불필요
./yt.sh audit --baseline "267 passed / 2 skipped"   # pytest 실측값까지 대조
```

- **오류(종료코드 2)가 0건**이어야 한다. 경고(1)는 상시 몇 건이 정상이며 사람이 판단한다
  (현행 기준선: §6 트레이서빌리티 미수록 FR **9건** = 경고)
- 종료코드 **3은 "확인 못 함"** 이다 — 0(이상 없음)과 절대 같이 보지 않는다
- 감사가 보는 것: pytest 기준선 5곳 일치 · V-U 번호(정본 = `tests/test_unit.py` 섹션 헤더) ·
  "다음 번호" 포인터 4계열 · FR·DQ 결번·중복 · §6 토큰 실재 · 버전 헤더 · CLI 명령 양방향
- 의도적 예외는 **문서 안의 표기**로 적는다(`(구현 없음 — …)`·`**테스트 미구현**`·`(구현 예정)`).
  그것으로 표현할 수 없는 잔여만 `audit_waivers.yaml`에 두며, **쓰이지 않는 waiver는 경고**로 올라온다
- **감사는 고치지 않는다**(FR38.1) — 아래 원칙이 그 이유다

- 불일치 발견 시: **문서와 코드 중 어느 쪽이 진실인지 임의로 정하지 않는다.** 불일치 목록을 만들어 사용자에게 보고하고 방향을 확인받은 뒤 수정
- "구현 예정" 표기가 남아 있는데 코드가 이미 존재하면 표기를 제거 (이건 자명하므로 바로 수정 가능)
