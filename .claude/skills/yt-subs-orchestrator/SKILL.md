# yt-subs 개발 오케스트레이터

Spec-First 원칙(NFR10) 아래 스펙 → 설계 → 구현 → 검증 → 문서 동기화 순서로 개발 작업을 조율한다.

**실행 모드: 서브 에이전트 오케스트레이션.** Agent 도구로 `.claude/agents/`의 전문 에이전트를 호출하고, 산출물은 파일(`_workspace/`)로 전달한다. 규모가 작은 변경(파일 1개·명백한 버그픽스)은 에이전트 분리 없이 이 세션이 직접 각 Phase를 수행해도 된다 — 단 Phase 순서와 산출물 기록은 유지한다.

## Phase 0 — 컨텍스트 확인

실행 모드를 결정한다:

1. `_workspace/`가 존재하고 사용자가 **부분 수정**을 요청 → 해당 Phase의 에이전트만 재호출 (이전 산출물을 입력으로 전달)
2. `_workspace/`가 존재하고 사용자가 **새 기능**을 요청 → `_workspace/`를 `_workspace_prev/`로 이동 후 초기 실행
3. `_workspace/` 없음 → 초기 실행

추가 확인: 요청이 운영 이슈(429·쿠키·멤버십)면 `extraction-ops` 스킬로, 대시보드 UI만이면 `dashboard-dev` 스킬로 위임 가능한지 먼저 판단한다.

## Phase 1 — 스펙 (spec-guardian)

- 입력: 사용자 요구 요약
- 작업: 해당 FR 존재 확인 → 없으면 FR 작성·기존 FR 수정, DESIGN.md 해당 섹션 갱신, 트레이서빌리티 갱신 (`spec-sync` 스킬 절차)
- 산출물: `_workspace/01_spec_summary.md` (FR 번호, 설계 섹션, 미해결 결정사항)
- **게이트**: 미해결 결정사항이 있으면 사용자에게 질문 후 진행. 스펙 없이 Phase 3으로 건너뛰지 않는다 — 문서 없는 구현은 다음 세션에서 맥락이 소실되기 때문이다.

## Phase 2 — 설계 검토

Phase 1 산출물이 기존 아키텍처 결정(DESIGN §10 DQ)과 충돌하는지 확인한다. 충돌 시 새 DQ 항목으로 결정을 명문화한 뒤 진행한다. 소규모 변경은 Phase 1에 병합 가능.

## Phase 3 — 구현 (pipeline-engineer)

- 입력: `_workspace/01_spec_summary.md`
- 작업: 스펙대로 구현. Docker 재빌드 필요 여부 판단 포함
- 산출물: `_workspace/02_impl_notes.md` (수정 파일, 이탈 사항, 재빌드 여부)

## Phase 4 — 검증 (qa-verifier, 점진 실행)

- 입력: `_workspace/02_impl_notes.md`
- 작업: `pipeline-verify` 런북 실행. **모듈 단위로 점진 실행** — 여러 모듈을 구현하는 큰 작업이면 모듈 완성마다 Phase 3↔4를 반복한다
- 산출물: `_workspace/03_qa_report.md`
- 실패 시: pipeline-engineer 재호출(실패 항목 전달) → 재검증. 동일 항목 2회 실패 시 사용자에게 보고하고 판단을 구한다

## Phase 5 — 문서 동기화 (spec-guardian)

구현 중 스펙 이탈이 있었으면 문서에 반영하고, "구현 예정" 표기를 "구현됨"으로 갱신한다. CLAUDE.md 변경 이력에 이번 작업을 1행 기록한다.

## 데이터 전달

- `_workspace/{NN}_{agent}_{artifact}.md` 컨벤션, 중간 산출물은 보존(감사 추적)
- 에이전트 호출 시 필요한 파일 경로를 프롬프트에 명시 (에이전트는 대화 컨텍스트를 공유하지 않는다)

## 에러 핸들링

- 에이전트 실패: 1회 재시도, 재실패 시 해당 Phase 결과 없이 진행하지 말고 사용자 보고
- 스펙-코드 충돌 발견: 어느 쪽이 진실인지 사용자 결정 필요 — 임의로 한쪽을 고치지 않는다
- 429 발생: 즉시 네트워크 작업 중단, `extraction-ops` 절차 안내

## 테스트 시나리오

- **정상**: "FR20.3 자막 전문 API 구현해줘" → P1 스펙 확인(FR20.3 존재, 설계 §2.9) → P3 server.py에 `/subtitle` + 경로 검증 구현 → P4 런북 ①②③⑦ + 경계면 비교(index.html `showSubtitle`의 `{text}` 파싱 대조) → P5 API 표 "예정"→"구현됨"
- **에러**: 구현 중 스펙 결함 발견(예: FR17.4 조건 결합 규칙 모호) → pipeline-engineer가 이탈 보고 → 오케스트레이터가 사용자에게 결정 질문 → spec-guardian이 FR 보정 후 재개
